# WebViewBridge 模块化拆分方案

> 🔧 本文档描述 WebViewBridge.java 的模块化拆分计划
>
> 最后更新：2026-07-04

---

## 一、背景

### 1.1 现状

- **文件大小**：WebViewBridge.java 经模块化拆分后已从 4700+ 行减少到约 1500 行
- **方法数量**：142 个 @JavascriptInterface 方法（部分已委托给子Bridge）
- **已完成拆分**：CarControlBridge、AppBridge、WallpaperBridge、MusicBridge、SystemBridge 等6个子模块
- **维护困难**：已大幅改善，各模块职责单一
- **风险高**：已降低，改动影响范围可控

### 1.2 拆分目标

- [ ] 主文件从 4700+ 行减少到 800 行以内
- [ ] 每个模块职责单一，便于维护
- [ ] 前端代码不需要修改（保持接口兼容）
- [ ] 逐步拆分，降低风险
- [ ] 每个模块都有独立的测试

## 二、拆分方案

### 2.1 总体思路

采用**委托模式（Facade）**：

```
┌─────────────────────────────────────────────────────┐
│                   WebViewBridge                       │
│              （统一入口，前端不用改）                   │
├──────────┬──────────┬──────────┬──────────┬──────────┤
│ CarCtrl  │  Music   │ Wallpaper│   App    │   ADB    │
│  Bridge  │  Bridge  │  Bridge  │  Bridge  │  Bridge  │
└──────────┴──────────┴──────────┴──────────┴──────────┘
```

- **WebViewBridge**：保持作为统一入口，所有 @JavascriptInterface 方法仍在这里定义
- **各个子 Bridge**：负责具体功能的实现
- **委托调用**：WebViewBridge 的方法只是简单转发给对应的子 Bridge

### 2.2 优点

1. **前端兼容**：JS 调用方式不变，不需要修改前端代码
2. **风险可控**：逐步拆分，每个模块可以单独测试
3. **职责清晰**：每个类只负责一个功能领域
4. **易于测试**：每个模块可以单独写单元测试
5. **节省上下文**：修改某个功能只需要读对应的子 Bridge

### 2.3 缺点

1. **方法定义仍在 WebViewBridge**：142 个方法的定义还是要占一些行数
2. **多了一层调用**：多了一次方法调用，但性能影响可以忽略

## 五、风险评估

### 5.1 风险列表

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| 拆分过程中引入 bug | 高 | 中 | 逐步拆分，每个模块单独测试 |
| 前端接口不兼容 | 高 | 低 | 保持 WebViewBridge 方法签名不变 |
| 性能下降 | 低 | 低 | 委托调用开销很小，可以忽略 |
| 代码量增加 | 低 | 中 | 拆分后总代码量会略增，但可维护性提升 |

### 5.2 回滚方案

如果拆分过程中出现问题：

1. 立即停止当前模块的拆分
2. 回退到上一个稳定版本
3. 分析问题原因
4. 修复后再继续
