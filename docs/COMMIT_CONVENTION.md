# C11Partner 代码提交规范

> 📝 本文档定义代码提交的规范和最佳实践
>
> 最后更新：2026-06-20

---

## 一、提交信息格式

### 1.1 格式

```
<type>: <subject>

<body>
```

### 1.2 Type 类型

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat: 添加氛围灯颜色控制` |
| `fix` | 修复 bug | `fix: 修复360全景自动弹出不生效` |
| `docs` | 文档更新 | `docs: 更新车控接口文档` |
| `style` | 代码格式调整 | `style: 格式化WebViewBridge代码` |
| `refactor` | 重构（不改变功能） | `refactor: 拆分WebViewBridge为多个模块` |
| `perf` | 性能优化 | `perf: 优化壁纸加载速度` |
| `test` | 测试相关 | `test: 添加CarControlManager单元测试` |
| `chore` | 构建/工具/依赖 | `chore: 升级Gradle版本` |
| `ci` | CI/CD 相关 | `ci: 添加GitHub Actions构建` |
| `revert` | 回滚提交 | `revert: 回滚上一次提交` |

### 1.3 Subject 要求

- 简短描述，不超过 50 个字符
- 使用动词开头（添加、修复、更新、优化等）
- 不用句号结尾
- 中文描述，清晰易懂

### 1.4 Body 要求（可选）

- 详细说明提交的内容
- 可以分点列出
- 说明修改的原因和影响

## 二、提交规范示例

### 2.1 简单提交

```
feat: 添加副屏胎压显示
```

### 2.2 带详细说明的提交

```
fix: 修复音乐信息不更新的问题

- 修复通知监听服务在某些情况下不工作的bug
- 添加权限检查，无权限时显示引导提示
- 优化音乐信息更新频率，从1秒改为2秒

Closes #123
```

### 2.3 文档提交

```
docs: 完善车控接口文档

- 添加Settings.Global属性列表
- 补充Logcat监控信号说明
- 更新验证状态
```

## 三、提交前检查清单

提交代码前，请确认：

- [ ] 代码可以正常编译通过
- [ ] 没有遗留的调试代码（如 System.out.println、Log.d 等）
- [ ] 命名符合规范（类名大驼峰，方法名小驼峰）
- [ ] 关键方法有注释说明
- [ ] 相关文档已更新（如果有接口变动）
- [ ] 代码索引已更新（如果有方法变动）
  ```bash
  python3 tools/generate_code_index.py
  ```
- [ ] API 文档已更新（如果有 JS 接口变动）
  ```bash
  python3 tools/generate_api_docs.py
  ```

## 四、分支规范

### 4.1 分支类型

| 分支 | 说明 |
|------|------|
| `main` | 主分支，稳定版本 |
| `develop` | 开发分支 |
| `feature/xxx` | 功能分支 |
| `fix/xxx` | 修复分支 |
| `release/xxx` | 发布分支 |

### 4.2 开发流程

1. 从 main 分支创建 feature 分支
2. 在 feature 分支上开发
3. 开发完成后合并到 develop 分支测试
4. 测试通过后合并到 main 分支
5. 打 tag 发布版本

## 五、代码质量要求

### 5.1 Java 代码规范

- 使用 AndroidX，不要用旧的 support 库
- 类名：大驼峰（PascalCase）
- 方法名：小驼峰（camelCase）
- 常量：全大写下划线分隔（UPPER_SNAKE_CASE）
- 缩进：4 个空格
- 每行不超过 120 个字符
- 关键方法必须有 Javadoc 注释

### 5.2 JS 代码规范

- 使用 ES6+ 语法
- 变量和函数：小驼峰
- 类和对象：大驼峰
- 缩进：2 个空格
- 字符串优先使用单引号
- 关键逻辑添加注释

### 5.3 注释规范

- Javadoc 注释必须包含：功能说明、参数说明、返回值说明
- 复杂的逻辑必须有行内注释说明
- TODO/FIXME 必须标注原因和预计完成时间

## 六、版本号规范

### 6.1 版本号格式

```
主版本号.次版本号.修订号
```

- **主版本号**：不兼容的 API 修改
- **次版本号**：向下兼容的功能性新增
- **修订号**：向下兼容的问题修正

### 6.2 示例

- `v1.0.0` - 第一个正式版本
- `v1.1.0` - 新增功能
- `v1.1.1` - 修复 bug
- `v2.0.0` - 重大更新，不兼容旧版本
